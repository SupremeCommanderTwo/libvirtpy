# How it works

## Three layers, one direction

```
libvirtpy.client   operations, sync + async clients, fake daemon
   │      │
   ▼      ▼
libvirtpy.xml   libvirtpy.rpc        (never import each other)
```

`libvirtpy.errors` (the base `LibvirtPyError`) is the only module all three share. A
test (`tests/tools/test_layers.py`) fails if a layer imports one it must not know.

## The wire protocol (`libvirtpy.rpc`)

libvirt's remote protocol is XDR over a stream: a 4-byte length, a 24-byte header
(program, version, procedure, type, serial, status) and an XDR payload.

- `rpc.xdr` is a small hand-written XDR codec.
- `rpc.protocol` is **generated** by `tools/gen_protocol.py` from libvirt's `.x` files:
  a dataclass per structure and a table of all 456 procedures. Never edit it.
- `rpc.session.Session` has no I/O at all: it turns calls into bytes and received
  bytes into results, matches replies by serial, decodes errors and pushed events,
  and answers keepalive pings.
- `rpc.sync.SyncRpc` (a reader thread) and `rpc.aio.AsyncRpc` (an asyncio task) only
  move bytes for a `Session`.
- `rpc.sockets`, `rpc.remote`, `rpc.remote_aio` find and open the transports (UNIX
  sockets, an `ssh` child process, TLS, TCP); `rpc.sasl` does SCRAM, DIGEST-MD5 and
  PLAIN with the standard library.

## Operations, written once

The logic of the client lives in `libvirtpy.client.operations`, as **sans-I/O
generators**. An operation `yield`s a `Request(procedure, arguments)` (here through the helper `on_domain`, which
first finds the domain from a reference) and receives the reply; it never touches a
socket:

```python
def start_domain_migration_post_copy(
    domain: DomainRef, *, flags: int = 0
) -> Operation[None]:
    """Switch a running live migration to post-copy mode.

    :param domain: the domain.
    :param flags: reserved, 0.
    """
    yield from on_domain(domain, "domain_migrate_start_post_copy", flags=flags)
```

A runner (`_runner.py`) drives it: synchronously for `LibvirtClient`, with `await` for
`AsyncLibvirtClient`. So there is exactly one implementation of every operation, and
the blocking and async clients cannot disagree.

`Request.procedure` is a real libvirt procedure name and the arguments are that
procedure's fields. `client.wire` converts a request into the generated argument
structure and the reply back into models, handles, numbers and `dict`s.

## Generated clients

`client.py` and `aio.py` are generated by `tools/gen_client.py` from the operation
modules: one one-line method per operation, plus a proxy class per kind of object.
Drift between operations and clients fails a test.

## How it is tested

- **Corpus:** the models parse and rewrite all of libvirt's own sample XML (10,728
  files) and validate against its RelaxNG schemas.
- **Synthetic daemon:** every public operation runs with sample arguments against a
  daemon that checks each request against the real argument structure.
- **Fake RPC server:** a real server on a socket for transports, TLS, SASL, events and
  streams.
- **Live tests:** read-only tests, and write tests that create and delete throwaway
  `lvxtest-*` objects, against a real `qemu:///system`.

## Adding an operation

1. Write the generator in the module of its area in `client/operations/`, with a full
   docstring.
2. `python tools/gen_exports.py libvirtpy.client.operations`, then
   `python tools/gen_client.py`.
3. Add a test; the synthetic-daemon test picks the operation up by itself.
